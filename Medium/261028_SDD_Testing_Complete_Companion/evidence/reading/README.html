Matrix isolation and rebuild inputs

matrix accepts only the pinned Ollama profile. Every live attempt receives a fresh container and CLI home on a Docker internal network. A separate relay has access to native Ollama and permits only the pinned model on Messages, Messages token-count and Chat Completions endpoints (including Claude's exact ?beta=true variant). Workers have no published ports or host/volume mounts. Each live attempt checks that direct public TCP access and direct host-Ollama access fail, the relay responds, and model-management requests are rejected. This is a constrained local lab, not a general network-exfiltration certificate.

CLI workers on internal network -> allowlisted relay -> native Ollama -> Metal

Relay logs contain route/model/settings, not prompts or response content. Missing or invalid audit logs fail the aggregate verdict. A client disconnect during response delivery is allowed only within the number of completed intentional interruption tests; upstream transport failures still fail. Every container and the exact UUID-owned relay/network are removed in finally. An interrupted batch retains completed reports and leaves unfinished coverage missing.

The image includes the complete test tree, support scripts, audit allowlist, placeholder .env.example, selected parent framework references, and normalized executable modes. matrix-requirements.lock (matrix-requirements.lock; source-only reference, not supplied) adds pinned MCP/async-test/build dependencies to the base Python lock. The build bakes all wheels plus the actual SDD CLI wheel into /opt/wheelhouse. Runtime pip installs use PIP_NO_INDEX=1 and touch only disposable venvs. No host pip/npm installation or host Claude/Copilot configuration change is required.

Live workers retain the 2 GiB/2 CPU limit. Offline deterministic/regression containers use 4 GiB memory and 2 GiB per tmpfs; their temporary filesystems are executable so the real installed CLI launcher can run. Native Ollama GPU memory is outside these container limits. Build records include source bytes, normalized file modes, recipe hashes, exact image IDs and resolved npm locks. Source, mode, runner or lock drift requires rebuilding. A newer dependency refresh must review both Python locks. Byte-identical rebuild limitations are documented below.

Reports are written immediately under runs/matrix-<UTC>-<id>/: one JSON per cell, summary.json, and relay.jsonl. Failed attempts are retained when a later run succeeds. Summaries distinguish selected coverage, the full local matrix and unresolved external requirements. The run directories and images are local and ignored by Git; preserve them and the uncommitted implementation changes for future replay. The original run smoke remains available as described below.

Rebuild and run from scratch

Prerequisites on another Mac: Apple Silicon, native Ollama 0.40.11 running, Docker Desktop with Linux ARM64 containers, Git and Python 3.11+. Preserve this working tree's lab additions/patch as well as the source commit: the current lab files are not yet committed to the remote branch. A checkout of that commit alone does not contain them. No host Claude, Copilot, npm or pip installation is needed. Start Docker/Ollama normally if they are not running.

On a fresh Ollama installation, install the base weights once:

ollama pull qwen3.5:9b-q4_K_M

Then, from enterprise-sdd/ (substitute your Python 3.11+ path):

/opt/homebrew/bin/python3.13 _tests/test_harness_runtime.py -v
/opt/homebrew/bin/python3.13 _tests/harness_runtime/lab.py prepare-ollama --config _tests/harness_runtime/config.ollama.json
/opt/homebrew/bin/python3.13 _tests/harness_runtime/lab.py build --config _tests/harness_runtime/config.ollama.json
/opt/homebrew/bin/python3.13 _tests/harness_runtime/lab.py check --config _tests/harness_runtime/config.ollama.json
/opt/homebrew/bin/python3.13 _tests/harness_runtime/lab.py run --config _tests/harness_runtime/config.ollama.json

prepare-ollama checks the server version and installed base digest, creates only the missing lab alias, then verifies the alias digest. It does not pull weights, overwrite a conflicting alias or change server settings. It is safe to repeat. A tag pulled in the future may have different bytes: that causes an explicit failure, not a silent model upgrade. Restore the recorded model cache or review and record a new configuration before adopting different bytes.

run warms the selected model for ten minutes and requires the recorded context and fully GPU-resident weights. Ollama may reuse a runner for identical weights and report the previously loaded alias. If the identity check stops on that condition, inspect ollama ps; stop only a model you own and are finished using before retrying. The runner does not unload someone else's model automatically. CLI calls can refresh Ollama's normal keep-alive interval. To release this lab's GPU memory after use, run ollama stop sdd-w30-qwen35:9b-64k.

The alias is the only persistent model addition and shares existing weight blobs. To remove it deliberately, use ollama rm sdd-w30-qwen35:9b-64k; retain the base model. GPU/unified-memory use belongs to the native Ollama process and is outside Docker's 2 GiB limit. CLI requests run sequentially. The 64k configuration is for this bounded smoke; GitHub recommends 128k for general Copilot use, which would require a separately recorded configuration.

For exact restoration, retain both model manifests and all blobs they reference from Ollama's model cache, the Ollama installer/binary version, the source patch, config/lock and image archives. The base tag alone is not an immutable backup. The recipe can rebuild fresh containers without cached images; byte-identical image reconstruction has the limitations described below.

Original smoke isolation boundary (run)

The host orchestrator uses Python 3.11+ standard library only and Docker. It requires no host pip/npm packages, global CLI upgrades, shell startup changes or edits to the host CLI configuration. Docker Desktop must be running.

Each attempt creates a new non-root container with a read-only root filesystem, all Linux capabilities dropped, no-new-privileges, resource limits and writable tmpfs directories for the synthetic project, home and temporary state. There are executable permissions on the isolated home tmpfs because Copilot unpacks its native runtime there; this grants no host filesystem access. There are no bind mounts, volumes, Docker socket mounts or privileged containers. The local check has networking disabled. Live runs use Docker bridge networking for provider access; network egress is not allowlisted, so this first increment must use trusted synthetic prompts. Network-exfiltration adversarial cases require an egress-controlled follow-up before being considered covered.

Selected tracked framework inputs and narrowly selected parent instructions, agents and the evolution reference are copied into the image; the complete parent repository and its Git metadata are not copied. The lab explicitly includes its uncommitted runner/tests and existing F.2 fixture files. New untracked framework implementation files are not included automatically: review/stage those before building. Symlinks and secret-like filenames in the selected inputs are rejected. This is not a general content secret scanner; review the source manifest before live use.

Credentials are read from named host environment variables, sent to the worker over stdin, and provided only to the corresponding CLI child process. They are never Docker environment entries, command arguments, build arguments or image layers. An agent could access a credential available inside its own environment; use dedicated restricted credentials and synthetic projects. Do not paste tokens into chat, commit an env file, or copy the host home/keychain into a container.

The worker gives the builder file tools and the reviewer read tools only; shell, fetch and MCP tools are excluded. Each role uses a fresh CLI configuration directory; no continuation/resume flags are used. Provider-returned session IDs must be present and distinct. That supports this smoke's context separation; it is not certification of every native reviewer route. The stock native profiles remain unmodified and unverified.

Exact replay versus rebuilding

run/check use the recorded immutable image ID, never an implicitly refreshed tag. They retain the actual dependency versions. Preserve the image with Docker's image save to an archive and restore it using image load if you need byte-exact replay on another ARM64 Docker host. Save the matching build records, source revision/patch, config and lock alongside the archive.

Rebuilding uses pinned base/CLI/Python versions and checks the top-level CLI npm integrity. Apt repositories and transitive npm dependency resolution can change; a rebuild is not guaranteed byte-identical. Its new image ID and resolved npm lock make that difference visible. Exact reproducibility also does not imply identical model output: provider behavior and sampling may vary.

Reports, failures and cleanup

Exit 0 means all selected checks passed; exit 1 means a failed/blocked run; exit 2 means setup/configuration failed. Timeouts terminate the CLI process group, with an outer Docker watchdog as backup. The orchestrator removes only its exact UUID-named container in finally; tmpfs state disappears with it. Images and build cache are retained for replay. There is no global Docker prune or host cleanup.

If the host process is forcibly killed, inspect Docker containers labeled sdd.lab=W30, confirm the exact UUID, and remove that container explicitly. A cleanup failure is included in the report with its precise name. Do not remove unrelated containers or volumes. Sanitized transcripts may still contain provider account details not recognized by redaction: keep run reports local and review them before sharing. Known supplied credentials and common token formats are redacted before host persistence; raw CLI config/home state is never exported.
